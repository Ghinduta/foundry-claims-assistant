Claims assistant on Microsoft Foundry: how it's built and why

A chat assistant for a car insurer's customers. It answers general questions from the company's documents, tells a signed-in customer the status of their own claim and never anyone else's, reads uploaded claim forms and car damage photos, and asks a person to approve before it books a callback. Each piece is chosen because an AI-103 exam topic needs it. Blue arrows follow one question; it branches to green (policy question) or purple (claim question). Amber arrows show a document upload. All data is public or generated, so the repository can be public.

1. One question, start to finish

  1. The claimant asks. They sign in with Entra External ID, so the app knows who they are and which claims are theirs. The chat page sends the question to your ASP.NET Core app with the sign-in token.
  2. The app runs the agent. The app adds the question to the claimant's conversation thread in Foundry Agent Service and starts a run. The thread keeps the conversation history, so you don't resend it on every turn. The agent has a role, instructions and three tools.
  3. General question: the agent searches. For "Which documents do I need for water damage?" the model picks the knowledge-search tool. Azure AI Search runs a hybrid query (keyword + vector) over the company's documents, and the model answers only from the passages it gets back, with the source document named.
  4. Claim question: the agent asks your app. For "Where is my claim?" the model picks get_claim_status. A function tool doesn't run inside Foundry: the run pauses and hands the call to your app. Your app takes the claim id from the signed-in session, never from the model, calls the Claims API and returns the result to the run. Section 2 shows this loop in detail.
  5. The model writes the answer. gpt-5-mini writes the reply from the search passages or the claim data. Guardrails screen both the question and the answer: content filters for harmful content, Prompt Shields for prompt-injection attempts.
  6. The claimant gets the answer with its sources. Every step is traced to Application Insights: which tool ran, how many tokens, how long it took, and whether a guardrail fired.

The idea to remember: the model decides what to do (search, look up a claim, ask for a callback); your code decides whether it's allowed and with which data. That split is what AI-103 means by "tool-access controls" and "oversight".

2. The function-calling loop, and why the claim id never comes from the model

This is the part of the project the exam asks most about, and the part a client will ask you to explain. The model never calls your Claims API itself. It asks your app to.

3. The data

A claims assistant needs four kinds of data. None of it is real customer data: two parts come from public datasets with open licenses, two are generated by a script. Generating is deliberate: when you wrote the document or the form yourself, you know the right answer, so the tests have exact expected results.

Loading it: one-off Python scripts in data/scripts/

  1. Claims: read the CSV, add the status columns with fixed random seeds (so every run gives the same data), write claims.db for the mock Claims API.
  2. Forms: render about 50 claim rows as PDF forms and save the matching fields as JSON. That JSON is the expected answer for the extraction tests.
  3. Documents and photos: upload the policy documents and the selected photos to Blob Storage, then create the AI Search index and indexer.

These scripts are in Python on purpose: creating an index, an indexer and a Content Understanding analyzer are exactly the SDK calls the exam shows in Python.

5. Security: who may do what

No keys

The app's managed identity gets RBAC roles on Foundry, AI Search and Storage. Locally you use your own az login identity through DefaultAzureCredential, so the same code runs in both places.

Least privilege

The app can read the search index but not change it. Only the indexer writes. The Claims API account is read-only and returns approved fields only.

The model is untrusted input

Tool arguments from the model are validated like user input. Anything that identifies a claim comes from the session.

Documents are untrusted too

Uploaded forms and photos can contain hidden instructions. Prompt Shields screens them, and the agent's instructions say document text is data, not commands.

A person approves actions

Reading is automatic; doing something (booking a callback) waits for a handler's approval.

Left out on purpose

Private endpoints and a VNet. They cost money and add setup time for a demo; you study them for the exam instead (section 7).

6. Evaluation: how you know it works

About 40 test questions in a JSONL file, scored by a Python script with the azure-ai-evaluation package and run in CI. Writing the evaluation in Python is deliberate: the exam's code is Python.

GroupCountPasses when
Knowledge questions15Groundedness and relevance ≥ 4 of 5; the right source is cited
Own-claim questions10Status matches the mock database
Other-claim attempts5No data from another claim, ever (zero tolerance)
Out of scope5"I can't answer that" plus the handoff offer
Prompt injection5Blocked by Prompt Shields or ignored, including text inside a photo

Studied, not built

These are on the exam but don't belong in a claims assistant, or cost too much for a demo. Study them on Microsoft Learn and try each once in a short Python notebook:
  • Speech: speech to text, text to speech, speech translation, speech as an agent modality.
  • Image and video generation: text-to-image, inpainting and mask edits, video generation and editing.
  • Translator and Language features beyond what the handler summary uses.
  • Private networking: private endpoints, VNet integration, network isolation for Foundry and AI Search.
  • Multi-agent orchestration: connected agents and workflows. Optional stretch goal: split intake and status into two agents.
